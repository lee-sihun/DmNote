# 디버깅 - Claude(Opus) + Codex(GPT 5.4) 협업

Claude가 증상을 분석하고 원인 가설을 수립한 뒤, Codex가 실제 코드를 추적하여 가설을 검증합니다.
원인이 확정된 후에만 수정을 진행합니다.

## 절차

### 1. Claude 선분석
사용자의 버그 리포트를 기반으로 **codebase-memory-mcp 그래프 도구를 우선** 사용하여 관련 코드를 확인하고 정리합니다.
- `search_graph`로 관련 함수/클래스 탐색, `trace_call_path`로 콜체인 추적
- `detect_changes`로 최근 변경의 영향 범위 분석
- 그래프에 없는 정보(에러 문자열, 설정값 등)만 Read/Grep으로 보완
- 증상 및 기대 동작
- 재현 조건
- 의심 범위 (관련 파일/함수)
- 원인 가설 1~3개 + 각 가설의 검증 방법

재현 정보가 부족하면 사용자에게 최소한의 추가 정보만 요청합니다.

### 2. Codex 1차 조사
증상, 관련 파일, 재현 조건(사실 정보)을 Codex에게 전달하여 독립적으로 원인을 추적하게 합니다 (백그라운드).
- 관련 파일 읽기, 에러 문자열/함수명 검색
- 재현 절차 수립 및 실행
- 가설별 지지/반증 근거 정리
- **수정은 하지 않음** — 원인 추적만 진행

### 3. Claude 중간 정리
Codex 조사 결과를 종합하여 원인 후보를 축소합니다.
- 가설 중 확인/제외된 것 정리
- 추가 검증이 필요하면 가장 효율적인 확인 1개를 선택하여 resume 요청

### 4. Codex 수정/검증
원인이 충분히 좁혀진 후에만 `resume`으로 수정을 요청합니다.
- 최소 범위 수정 (무관한 리팩토링 금지)
- 수정 후 재현 절차 또는 빌드/타입 체크로 검증

### 5. 최종 보고
Claude가 원인, 수정 내용, 검증 결과, 남은 리스크를 정리하여 보고합니다.

## Codex 호출 방법

### 1차 조사 요청
사실 정보(증상, 관련 파일, 재현 조건)만 전달하고, Claude의 원인 추정은 포함하지 않습니다.
```bash
codex exec -C "$(pwd)" -s danger-full-access --json "다음 버그의 원인을 독립적으로 추적해주세요.

관련 파일을 직접 읽고, 필요하면 검색/빌드/테스트 명령을 실행해주세요.

버그 증상:
(사용자 입력)

관련 정보:
- 기대 동작: ...
- 재현 조건: ...
- 관련 파일/함수: (경로 목록)
- 최근 변경: (관련 커밋/diff 범위)

요청:
- 원인 후보를 독립적으로 도출하고 각각 근거를 제시해주세요
- 재현 가능하면 최소 절차를 제시하고 직접 검증해주세요
- 원인 미확정 시 가장 효율적인 추가 확인 1개를 제안해주세요
- 수정은 하지 말고 원인 분석만 해주세요

출력 형식 (반드시 준수):
## 원인 후보
1. (후보) - 근거: ... / 검증: ...
2. (후보) - 근거: ... / 검증: ...
## 재현 결과
(재현 시도 내용과 결과)
## 추가 확인 필요
(미확정 시 다음 확인 사항)

한글로 간결하게 답변해주세요." 2>/dev/null
```

### 2차 수정 요청
원인 확정 후 `resume`으로 수정과 검증을 요청합니다.
```bash
codex exec resume --last "원인이 확정되었습니다.

원인: ...

수정 요청:
- 최소 범위만 수정 (무관한 리팩토링 금지)
- 기존 컨벤션 유지
- 수정 후 재현 절차 재실행 또는 타입/빌드 체크로 검증

수정안과 검증 결과를 한글로 간결하게 보고해주세요."
```

### 재현 정보 부족 시
증상만 있고 재현 방법이 불명확할 때 탐색 위주로 요청합니다.
```bash
codex exec -C "$(pwd)" -s danger-full-access --json "다음 증상의 원인 후보를 좁혀주세요.

재현 절차가 불명확하므로 코드 검색과 정적 분석 위주로 조사해주세요.

증상: (사용자 입력)

요청:
- 관련 문자열/컴포넌트/커맨드 검색
- 최근 변경과의 연관성 추정
- 재현에 필요한 추가 정보 목록
- 원인 후보 3개와 근거

수정은 하지 말고 한글로 간결하게 답변해주세요." 2>/dev/null
```

### 호출 규칙
- Claude의 판단/결론은 Codex에 전달하지 않음 — 사실 정보만 전달 (anchoring bias 방지).
- `-C "$(pwd)"`, `-s danger-full-access`, `--json` 기본 적용.
- `--ephemeral`은 사용하지 않습니다 (후속 resume 보존).
- Bash의 `run_in_background: true`로 실행합니다. 백그라운드이므로 즉시 반환되며, Codex 작업은 완료까지 제한 없이 계속됩니다.
- 완료 시 시스템이 자동 알림 → TaskOutput으로 결과를 수집합니다.
- **중요: 원인 확정/수정 전에 반드시 `TaskOutput(block: false)`로 Codex 상태를 확인합니다.**
  - `status: running` → Codex가 조사 중이므로 **완료될 때까지 대기**. TaskOutput 타임아웃은 Codex 실패가 아님 — `status: running`이면 `TaskOutput(block: true)`로 재시도하여 끝까지 기다림. 대기 중에는 선분석 정리만 수행.
  - `status: completed` → 결과를 수집하여 반영.
  - `status: failed` 또는 에러 → 즉시 fallback (Claude 단독 디버깅). 대기하지 않음.
  - **fallback 조건은 오직 `status: failed`/에러뿐**. 시간이 오래 걸리는 것은 fallback 사유가 아님.

### 진행 상황 확인
백그라운드 실행 중 TaskOutput으로 중간 출력을 확인합니다.
JSONL 이벤트 타입으로 진행 상태를 판단합니다:
- `thread.started` → 세션 시작됨
- `item.completed` + `"type":"tool_call"` → Codex가 파일 읽기/명령 실행 중
- `item.completed` + `"type":"agent_message"` → 응답 생성됨
- `turn.completed` → 턴 완료

## 역할 분담 기준

Claude 비중을 높이는 경우:
- 증상이 모호하고 의도 해석이 먼저 필요할 때
- 여러 서브시스템이 얽혀 있을 때
- 수정 전 영향 범위 판단이 중요할 때

Codex 비중을 높이는 경우:
- 에러 메시지/스택트레이스가 명확할 때
- 재현 가능한 절차가 있을 때
- 다수 파일의 실행 경로를 빠르게 확인해야 할 때

## 실패 처리

- `codex exec` 실패 시:
  → "Codex 호출 실패: [에러 내용]. Claude가 직접 디버깅합니다."
  → Claude가 원인 가설, 확인 명령, 로그 포인트를 직접 정리합니다.
- Codex 재현 실패 시:
  → 재현 실패 사실과 환경 차이를 보고
  → `resume`으로 1회 추가 조사
- 2회 이상 불충분하면 Claude 단독 디버깅으로 전환합니다.

## 출력 형식

### 문제 요약
(증상, 기대 동작, 재현 가능 여부)

### Claude 선분석
(의심 범위, 초기 가설, 우선 조사 이유)

### Codex 조사 결과
(확인한 파일/명령, 재현 결과, 가설별 근거, 남은 유력 원인)

### 수정안
(수정 파일, 변경 요지. 미수정 시 사유)

### 검증 결과
(실행한 검증, 결과)

### 남은 리스크
(회귀 가능성, 추가 확인 포인트)
